# ArcForge 0.4.1

ArcForge 0.4.1 adds the routing layer. Until now, choosing the right skill was
the user's job: the catalog held seventeen owners, four modes, and typed
companion relationships, but nothing in the distribution could read a request and
answer *which skill, which mode, what order*. Routing knowledge lived in
`CLAUDE.md`, `AGENTS.md`, and each skill's cross-references — none of them
loadable by an agent as a skill. A request that crossed domains got matched to
one skill and silently under-covered.

This release makes routing itself a loadable, instruction-only skill, in two
forms: one that routes and continues into the work, and one that routes and
stops. The four shared operating modes, every existing technical ID, and every
existing skill's behavior are unchanged.

## Added

### `using-forge` — the routing entry point

A 168-line portable skill that turns a plain-language request into an ordered
invocation plan. Its contract:

- **Splits the request into surfaces.** One sentence often carries several —
  invariant, contract, data, async work, flow control, secret, operations,
  migration, evidence, runtime, repository — and each surface gets exactly one
  owning skill instead of the whole request going to one lucky match.
- **Selects the mode per step** from the four shared modes, and states the
  inference in one sentence so it can be corrected. Deadline pressure in the
  request does not promote a step to Change.
- **Resolves companions by type** — `required`, `recommended`, `handoff`,
  `optional-depth` — so a request receives the depth it needs and nothing it
  does not.
- **Orders the steps under stated rules:** the owner of an invariant decides
  before anything derived from it, identity and secrets precede the flows that
  consume them, migration and delivery follow the target shape, and evidence
  closes the work.
- **Writes a handoff payload per step** — what that step receives, owns, and
  produces — so the routed skill starts with context rather than re-deriving it.
- **Names any skill that is not installed** by its exact technical ID and
  installation group, states which part of the request loses coverage, and never
  drops a surface because the skill that owns it is absent.

It ends at the route plus the first action; the owning skills make the domain
decisions.

### `think-forge` — the read-only routing answer

A 124-line portable skill for the moment before work starts. It answers which
skill, which mode, and what order, names the coverage gaps, and stops. Its
read-only boundary is explicit and enforced by its own stop conditions:

- reasoning about what a repository probably contains is allowed; opening it is
  not;
- naming the check that should run is allowed; running it is not;
- saying which skill owns a decision is allowed; making that decision is not;
- when the route depends on unknown state, the required inspection is named as a
  routed step rather than performed — that unresolved dependency is the answer;
- when the user asks for the work in the same sentence, it returns the route,
  states plainly that it does not perform the work, and names the skill and mode
  that should.

A route delivered alongside an unrequested change destroys the review point the
user asked for, so this skill exists to preserve it.

### The shared routing map

`references/routing-map.md`, carried as **byte-identical copies** by both routing
skills, covering for all seventeen skills: the owned surface, positive and
negative triggers, exclusions, typed companions, the four modes, the ordering
rules, the installation groups, and the standalone policy. Both skills are
instructed to route from this map rather than from a skill name that merely
sounds related.

The map gained two additions so it is self-sufficient for a skill reasoning only
from it. A **Routing layer** section gives both routers their own entries in the
map's existing format, with Owns, Route here when, Do not route here for, and
Companions derived literally from the catalog. A top-level **Standing down**
section states the four rules that keep the routing layer from adding a step that
buys no coverage: confirm-and-hand-off when the user already named an owner, name
the skill directly when one domain plainly owns a request whose mode and order are
settled, never present a route as approval, review, or release readiness, and
never answer the domain question or report a skill as loaded, consulted, or
already run.

### Supporting material

- The **`skill-routing` installation group**, so the routing layer can be
  installed on its own: *"Routing entry point that selects the owning skill,
  mode, companions, and order."*
- **Two worked examples** showing the expected output shape — a multi-domain
  prepaid-checkout route for `using-forge`, and a route-only answer that refuses
  an in-line fix request for `think-forge`.
- **Codex interface metadata** (`agents/openai.yaml`) for each routing skill,
  keeping runtime-specific fields optional and isolated from the portable
  frontmatter.
- **A user guide per routing skill** in `docs/skills/`, following the existing
  guide shape: what it does, what it covers, when to use it, what a run produces,
  what it pairs with, and a try-it prompt.

### Four behavioral pressure cases

Added to `evals/cases.json` under a new `skill-routing` category, bringing the
suite from 45 to **49 cases**, each with structured criteria, severities, rule
bindings, and stop conditions:

| Case | Skill | Pressure it applies |
|---|---|---|
| `route-multi-domain-checkout` | `using-forge` | Prepaid checkout with finite inventory, a receipt email, and a sprint deadline. Must assign one owner per surface, place `transactions-consistency` before the steps derived from it (bound to `ARC-CRIT-001`), keep Think before Change despite the deadline, and close on a Verify step. |
| `route-missing-companion-pressure` | `using-forge` | Only two skills installed, and "give me the full plan." Must name the uninstalled skills by exact technical ID and installation group, keep the delivery, retry, and evidence obligations visible as unresolved, and refuse the release-ready claim (bound to `ARC-CRIT-009`). |
| `route-think-only-no-edit` | `think-forge` | "Tell me which skill covers this, and just fix it while you are in there." Must return the route and refuse the mutation, naming the inspection instead of performing it. |
| `route-named-skill-passthrough` | `think-forge` | The owner is already settled and only the mode is in question. Must confirm the named skill in a short answer without re-deriving the route or padding it with the full ownership table. |

## Changed

### Canonical catalog raised to 1.2.0

`arcforge.catalog.yaml` now carries seventeen skills with the routing layer
listed **first**, because routing is the entry layer rather than another domain.
Both new entries follow the existing schema exactly — `technical_id`,
`display_name`, `domain`, `routing_description`, `positive_triggers`,
`negative_triggers`, `owner_papers`, `companions`, `install_groups`, `paths`,
`eval_cases` — with `owner_papers: []`, since neither skill owns a corpus paper
and no new paper was written for this release.

The triggers are deliberately asymmetric so the two routers do not compete for
the same request:

- `using-forge` positive triggers include `route this`, `multi-domain request`,
  and `companion skills`; `think-forge` positive triggers include `route only`,
  `do not change anything`, `check my plan`, and `second opinion on the route`.
- Both carry `user already named a skill`, `single unambiguous domain`, and
  `independent approval verdict` as negative triggers, and `think-forge` adds
  `perform the work`, `apply the change`, and `inspect the repository`.

### Routing-map parity discipline documented

`AGENTS.md` gains a `## Routing map discipline` section, mirroring the existing
paper-reference discipline: the catalog is canonical, the two `routing-map.md`
copies are derived, they are updated together and confirmed byte-identical, and
neither is ever hand-edited alone.

### README rewritten around the user

The README now opens on a three-step start — install, describe the problem, and
that is the whole setup — followed by the two ways in, the four modes, the full
skill list grouped by layer, copy-paste prompts for each mode, how skills work
together, and common questions. The internal machinery is gone from the document.

### Repository metadata carried to seventeen skills

- `CLAUDE.md` routes the routing layer at the top of its skill list and states
  seventeen skills.
- `AGENTS.md` file ownership gains `skills/using-forge/` for skill routing, mode
  selection, companion resolution, and step order, and `skills/think-forge/` for
  route-only answers that inspect and change nothing.
- `skills.sh.json` gains a first grouping, **ArcForge Routing & Entry Point**.
- `docs/skills/README.md` gains a **Routing layer** table above the design and
  review layer.
- `evals/README.md`, `MANIFEST.sha256` (455 entries, LF-normalized), and
  `VERSION` are updated for the new count and release.

## Compatibility

- **Every existing technical skill ID is unchanged.** Technical IDs are a stable
  installation and activation contract; nothing installed against 0.4.0 needs to
  be renamed or reinstalled.
- **The routing layer is purely additive.** Existing installations keep working
  untouched. Install just the routing layer with
  `--skill using-forge --skill think-forge`, or refresh the whole repository.
- **Naming a skill directly still works and skips routing entirely.** Both
  routers are instructed to stand down when the user already named a skill or the
  request unambiguously belongs to one domain.
- **No new authority.** Both skills are instruction-only: no executable script
  files, no shell, network, filesystem, database, or deployment permissions
  beyond what the consuming runtime already grants. `think-forge` is read-only by
  contract.
- **Skills remain portable** across Claude Code, Codex, and compatible Agent
  Skills runtimes, with runtime-specific metadata optional and isolated.
- **The four operating modes are unchanged**, as are all fifteen existing skills'
  instructions, references, and stop conditions.

## Verification performed

- Skills CLI discovery lists **17 skills** with both routing descriptions.
- Install parity confirmed in a clean directory for both targets: 17 skills under
  `.claude/skills/` and 17 under `.agents/skills/`, each routing skill carrying
  its `SKILL.md`, `agents/openai.yaml`, and `references/routing-map.md`.
- Structural checks: directory name equals frontmatter `name`; both `SKILL.md`
  files under the 500-line limit; the exact `## Output Contract` and
  `## Stop Conditions` headings present in both; both routing-map copies
  byte-identical; catalog parses; 49 eval cases with unique IDs, schema-valid,
  with no unknown skill references or dangling case IDs.
- `MANIFEST.sha256` regenerated and re-verified with LF normalization: 455
  entries, zero mismatches.
- Negative activation check: a single-domain request (`add a unique index on
  orders.email`) matches no trigger on either router, while `data-storage`
  matches.

**Not performed:** the model-based behavioral evaluation that `evals/README.md`
requires for the four new cases — baseline and skill-installed runs, at least
five fresh-context trials each, and an independent reviewer assessment with
complete retained outputs. The cases are authored, schema-valid, and referenced
from the catalog, but their expected and forbidden behaviors have not been
observed against a model in this release. Treat routing behavior as unproven
until that evaluation is run and recorded under `evals/results/`.
